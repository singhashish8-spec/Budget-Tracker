# Open-decisions log

One row per question or decision, append-only. Never delete a row; when a
decision's status changes, edit that row's *status* text in place and note
the date of the change — that's the one exception to "append-only." This is
the fastest way for a new session to get the project's whole decision
history in one screen.

| Question | Status |
|---|---|
| Should the app have a server/backend component? | **Decided 2026-07-14**: no — fully offline-first, device-local, no server. All native capability comes through the Capacitor bridge. See `roadmap/architecture.md`. |
| Should money be stored as floats or integers? | **Decided 2026-07-14** (implicit in the original schema, confirmed by `roadmap/architecture.md`): integer paise/rupee units, never floats. Never introduce a float into a money column. |
| Should the app load its UI remotely (`server.url`) or bundle it into the APK? | **Decided** (era unclear, confirmed current as of the 2026-08-01 repository study): bundle into the APK. A remotely-loaded page bridged to SMS/camera/biometrics would bypass Play Store review of runtime behavior, and would break offline use. |
| How should database migrations be allowed to change the schema? | **Decided** (present since the schema's earliest versions, confirmed by `roadmap/architecture.md`): strictly additive — `ADD COLUMN`, `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX` only. Enforced in code by `assertNonDestructive`, which regex-scans every migration for `DROP`/`DELETE`/`TRUNCATE` and throws before any statement runs. Never drop a column, even a dead-looking one — an older OTA web bundle may still read it (see the OTA/APK version-skew decision below). |
| How should GitHub Pages actually serve OTA update files? | **Decided 2026-07-21** (PR #2, corrected from a first wrong guess in PR #1): commit `latest.json` + the bundle zip directly to `main` root, because this repo's Pages source is configured as "deploy from branch: main /(root)," which silently ignores GitHub Actions—based deploys. |
| Should the OTA publish job run (and commit a new bundle) on every push, or only on a real version change? | **Decided 2026-07-21** (PR #3): gate on `latest.json`'s content (driven by `web-version.txt`), not the zip's bytes — builds aren't byte-reproducible, so gating on bytes would "change" on every run. |
| Should the on-device database be encrypted at rest? | **Decided 2026-07-22** (PR #17), reversing an earlier default: **no** — removed SQLCipher entirely after its Android-Keystore-derived key could be lost across an app update, bricking the database on every update. Protection now rests on the Android app sandbox; only the JSON auto-backup ever leaves the device, never the raw database file. `README.md` was not updated to match at the time — see the doc-drift row below. |
| Should the app call a cloud AI (Gemini) to parse receipts/bank statements? | **Decided 2026-07-26** (PR #41): **removed entirely.** It was the only part of the app sending personal financial documents to a third party, needed an API key almost nobody set, and could fail or cost money at the worst moment. Lost capability: importing a bank-statement file or scanning a paper bill — both went through Gemini. SMS auto-capture (rule-based, not AI) was untouched. |
| Should tapping a warranty/EMI/bill/subscription card open it for editing, or for viewing? | **Decided 2026-07-26** (PR #41): viewing — a new read-only `DetentSheet` dashboard by default; editing is a deliberate second tap. Reasoning: you open a card to *check* something far more often than to change it. |
| Should envelope (zero-based) budgeting replace plain budgets? | **Decided 2026-07-26** (PR #42): no — opt-in, off by default, coexists side-by-side with plain calendar/pay-cycle budgets. |
| Should "Reset app" just delete the database, or also the auto-backup snapshots? | **Decided 2026-07-26** (PR #43): also clear the auto-backup snapshots (`clearAutoBackup()`) — otherwise the very next launch finds a snapshot and hands the just-deleted data straight back. Confirming requires typing "RESET." |
| Should haptic feedback fire on every touch, or only on meaningful state changes? | **Decided 2026-07-26** (PR #44): tiered, state-change-only (tap/tick/success/error), explicitly modeled on why "iOS feels good" — firing on every touch is what makes an app feel cheap and costs battery. User-adjustable Full/Light/Off given how much Android vibration hardware varies. |
| How should the cost of visual "depth" effects (skins) scale across device capability? | **Decided 2026-08-01** (PR #48): a tiered depth engine (`max`/`balanced`/`off`), auto-detected once from `deviceMemory`/`hardwareConcurrency` and stored; unreadable or ≤4GB/≤4-core devices default to `balanced`. No tier is ever allowed to change layout, only visual cost — switching tiers can never reflow a screen. The motion setting and OS reduced-motion preference always outrank the tier. |
| How should Liquid Glass's edge-refraction effect be implemented? | **Decided 2026-08-01** (PR #48): a decorative overlay layer with an SVG `feDisplacementMap`, not `backdrop-filter: url()` — Android WebView support for the latter is unreliable across versions this app actually runs on, and it fails by rendering *nothing*, not a degraded effect. |
| Where should the on-device error/diagnostics log be stored — a DB table or `localStorage`? | **Decided 2026-08-01** (PR #49): `localStorage`, deliberately. The failures that matter most are the database failing to open or a migration throwing — a log living inside the database can't record the database failing to load. `localStorage` is available before the store is and needs no migration. |
| Should the edge-swipe-back gesture be added as part of the UI/UX audit? | **Researched, deliberately parked** (`docs/PROJECT_HISTORY.md` §8, date not separately recorded — carried forward as of 2026-08-15): dropped, not deferred. Android's own predictive-back gesture (`enableOnBackInvokedCallback`, `targetSdkVersion 36`) already covers this system-wide. Revisit only if Android's system gesture is ever found insufficient. |
| Should `.env.example` document a client-side `VITE_GEMINI_API_KEY`, or should it and the related README section be deleted now that AI parsing is gone? | **Decided 2026-08-15** (Session 13): deleted. `.env.example` now states plainly that no environment variables are required; the README's "Configuring the placeholders" section was rewritten to match (see `history/sessions/2026-08-15-session-13.md`). No backend-proxy plan exists or is planned, so keeping that option open was inventing a roadmap item that didn't exist. |
| Are PRs #34 and #37 (Jules) safe to close as superseded by #38? | **Decided 2026-08-15** (Session 13): yes, confirmed by diff, not assumption — both PRs were diffed line-by-line against current `main`. Every line of #34's fix (sql.js pin, CSV-injection regex) and #37's fix (DB connection-consistency check) is present on `main`, in most cases byte-identical. #37 would additionally have reintroduced a hand-committed `release/` zip that #38 deliberately removed. Both closed on GitHub with the diff evidence in the closing comment. |
| Should `docs/repository-study.md` (PR #47) be merged as-is? | **Decided 2026-08-15** (Session 13): no — its content is superseded, not merged verbatim. It was recovered, updated to current state, and folded into `roadmap/architecture.md` as part of Session 12/13's documentation work. PR #47 closed on GitHub, pointing to `architecture.md` as its successor. |
| How should this project's documentation be structured going forward? | **Decided 2026-08-15** (Session 12): adopted the structured `docs/history/` + `docs/roadmap/` + `docs/features/` + `docs/engineering/` system from `documentationandgitplaybook.md` in full, backfilling history from the recovered complete git/PR record rather than starting the historical record from this session forward. `docs/PROJECT_HISTORY.md` kept as a legacy reference, not deleted. |
| Is the pull-to-refresh gesture (Home/Transactions) reliable? | **Decided 2026-08-15** (Session 13): the specific mechanism flagged as questionable in PR #60 — `preventDefault()` not being called until after an 8px pull-intent threshold, giving the browser's compositor several early events to potentially commit the touch sequence to native scrolling first — was real and has been fixed (`preventDefault()` now fires from the first pixel of downward movement at the top). Verified via a real headless-browser harness mounting the actual component; full end-to-end confirmation (a completed pull triggering `onRefresh`) hit a Chromium DevTools Protocol touch-simulation limitation unrelated to the fix (confirmed present on the pre-fix code too) — see `history/findings.md`. Not confirmed on a real device, consistent with every other gesture change in this project's history. |
